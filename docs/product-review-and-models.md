# Product review and model controls

Team → **Edit models & fallback** configures each seat's preferred provider, model, reasoning effort and up to three ordered backups. The saved preference and actual running model are separate. Changes apply to the next run. Automatic fallback can be toggled in Team; an empty custom backup list means wait for the preferred provider. Existing automatic policies are preserved.

Codex choices come from the installed CLI's local model catalog plus explicitly configured models. The catalog timestamp is shown; catalog membership does not guarantee account access. Claude offers its four aliases plus `engines.claude.models`. Perplexity offers its built-in list, the models recorded in `data/perplexity-models.json` by `npm run models:refresh` (one read-only `models_list` call through the relay; the listing date is shown) and `engines.perplexity.models`; a model's recorded reasoning-effort set is enforced on save, and a model that takes no effort parameter (DeepSeek V4 Pro) is called without one. Unknown models, invalid effort levels, duplicates and incompatible role/provider assignments are rejected atomically. Perplexity is a thinking provider with a local Claude relay, so it cannot rescue an unavailable Claude relay or run implementation/QA. There is no silent substitute model. If all eligible providers are held, the job waits with its state intact. Global provider holds apply to every model on that provider.

New, unstarted root feature plans are enrolled when they reach the implementation queue (after dependencies). Existing in-flight work and submitted rework are not automatically re-enrolled. The independent review includes the Principal PM and relevant technical principal(s), plus UX, trading workflow and quant research perspectives when relevant. The EM synthesizes after first judgments and, when needed, one bounded challenge round for at most two objecting reviewers. Initial judgments are retained. At most two product reviewers run simultaneously; one capacity slot remains for QA/SRE when total capacity exceeds one. At capacity one, reviews run sequentially after higher-priority QA/SRE work. All runs use ordinary admission, daily budgets and provider fallback.

Every report identifies users, benefits, drawbacks, alternatives, evidence, conditions, architecture, rollout and success criteria. Support cannot contain unresolved conditions. Every required reviewer, including the EM, must support before implementation; an EM summary cannot overrule dissent. Problems appear in Inbox with **Revise & review**, **Retry failed reviews**, **Defer plan** and **Reject plan**. Deferring/rejecting the plan holds work and preserves the ticket and code. Corrections create a new revision, not an unbounded automatic debate. A changed approved scope or principal architecture record automatically gets a fresh review; earlier approval becomes stale immediately.

For enrolled features and their slices, a feedback review of the exact QA-passed commit precedes publication. A separate reviewer clone is pinned to that commit. Changing the commit requires fresh feedback. This supplements requester acceptance and independent QA; final merges remain owner-controlled. Owners may also request feedback on existing tasks. Supplied dashboard evidence and repository artifacts can be reviewed; these seats have no live broker access and no newly granted browser/production permissions. Missing visual or experimental evidence must be reported, not invented. Quant research is invoked for signal/strategy/forecast/backtest proposals, not every UI change.

Reports and revision history are durable in the desk database. A restart marks interrupted calls failed while retaining completed judgments; an explicit retry resumes only failed work. A provider failure permits one bounded fallback retry. First-review prompts omit concurrent peer conclusions, including from Perplexity context packs; challenge/synthesis receive recorded reports explicitly.

Implementation: `src/product-review.js`, `src/team-settings.js`, scheduler/publisher/merge guards and v2 UI. No new dependencies or database migration.
