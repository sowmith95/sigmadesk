## Proposed follow-up: Model Council and manager model routing

Status: researched and locally reviewed, not implemented. No council jobs, account connections, new tickets or paid reviews were started for this proposal.

### Findings

- The current `src/advisors.js` runs a reviewer and then a challenger sequentially, through key-based APIs. It permits one review job and accounts for that job as one concurrency slot. Parallel panels need per-member scheduling and durable member outcomes.
- Perplexity's [current Computer announcement](https://www.perplexity.ai/en-GB/hub/blog/model-council-comes-to-computer) describes a selectable council of two to eight models. This is a product capability; available models must be discovered for this account rather than copied from examples.
- Important qualification to the previous API-only setup advice: [Computer MCP](https://docs.perplexity.ai/docs/getting-started/integrations/computer-mcp-server) uses account OAuth and account credits, without a separate API key. Its documented model discovery and explicit-model calls offer a supported integration route. The documented modes do not name Council, so native Council selection through MCP remains unverified. If it is not exposed, separate explicit-model threads can supply the independent reviews. Computer MCP is not configured in the local Codex configuration or exposed in this session. The Mac is currently locked; its desktop picker could not be checked, while the local desk health endpoint remains responsive.
- [Agent API](https://docs.perplexity.ai/docs/agent-api/quickstart) is a separate key-based, pay-as-you-go route. The [Perplexity CLI](https://docs.perplexity.ai/docs/cli/overview) is for Search API access and needs a key; installing it does not by itself provide Council or subscription execution. [Router](https://docs.perplexity.ai/docs/router/routing-and-reliability) is private preview and addresses deployment failover for a requested model, so it should not be a dependency of this plan.
- [OpenAI's orchestration guidance](https://developers.openai.com/api/docs/guides/agents/orchestration) supports a manager retaining ownership while using bounded specialists. [Karpathy's council prototype](https://github.com/karpathy/llm-council) demonstrates independent opinions, anonymized peer assessment and a chair's synthesis; use the pattern rather than adding its separate application stack.
- Research on [sycophancy in debate](https://arxiv.org/abs/2509.23055) and [identity bias](https://arxiv.org/abs/2510.07517) identifies premature agreement and model-identity effects. Independent first passes, blind assessment and preserved dissent are design recommendations inferred from these findings, not a guarantee of better accuracy.

### Ownership and triggers

The Engineering Manager convenes the Architecture Review Board, specifies the question, reviewer lenses and resource envelope, and owns staffing/sequencing. The relevant principal chairs technical decisions and records an Architecture Decision Record. DBA owns database contracts, SRE owns incident hypotheses, and PM owns product evidence in their respective councils. QA can request focused contract/risk review while retaining its separate commit-pinned test verdict. Builders escalate ambiguity to the manager. Support and the deterministic watcher keep their current lightweight paths.

Suggested triggers after the pilot: high-risk or L/XL design; cross-component contracts; migrations, money/order safety or security changes; consequential release-policy decisions; two failed QA rounds indicating a contract gap; unresolved principal disagreements; recurring incidents with competing root causes. During urgent incidents, a council must not delay the existing containment/escalation path. Routine S/M work uses the established single-worker and independent-QA workflow.

The manager may recommend model IDs from the approved catalog for that job, with a reason. The scheduler resolves the effective provider/model using owner preferences, authenticated account availability, quotas, context/tool needs, measured quality, latency and cost. This is per-job routing; it does not rewrite the owner's saved seat defaults.

Start model-fit evaluation with the current Claude/Codex executors and the Kimi architecture, Gemini systems/frontend, Grok reliability and GLM efficiency advisory candidates. These are hypotheses to test. Keep execution eligibility separate from review eligibility: a model that can return a review is not automatically a sandboxed engineer. Prefer two distinct model families in a council; different provider endpoints serving the same model family do not provide that diversity. If only one family is available, label the result a single review and expose the unmet council requirement. Do not silently reduce quality or report a full panel when reviewers are missing.

### Council contract

1. Freeze one bounded, redacted brief with the owner question, alternatives, constraints, acceptance criteria, referenced files/lines and the relevant commit/base SHA or design-content hash. Each member receives that same evidence plus a narrow lens, without seeing peer answers.
2. Request two reviewers initially; offer an optional third lens. For the current four-slot desk, run at most two review members concurrently, count every active member and coordinator, and preserve capacity for QA/SRE. A third member waits for a slot. Durably reserve resources before dispatching each member and the synthesis step.
3. Store each member's verdict, actionable findings, evidence references, assumptions, missing information, proposed tests, actual provider/model, usage units and completion state. Persist Computer `thread_id` and input identity before follow-ups where the transport permits. A timeout may leave remote work running: reconcile the same thread rather than starting another paid task blindly.
4. Allow at most one focused cross-critique round when there is a material disagreement. Hide model names from assessment prompts while retaining identities in the audit record and UI. Avoid all-to-all ranking loops.
5. The domain chair synthesizes a recommendation, alternatives, conditions, unresolved dissent and testable follow-up actions in an ADR. Evidence outweighs vote count. Insufficient or contradictory evidence remains explicit. A council does not grant a QA verdict, publication permission or final merge approval.
6. New code/base/design inputs invalidate the applicable review evidence. Reuse completed reviews only for identical frozen inputs and the same review policy. Durable states distinguish queued, running, partial, failed, awaiting decision and decided outcomes.
